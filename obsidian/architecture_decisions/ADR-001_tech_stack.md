# ADR-001: Вибір технічного стека

**Дата:** 2026-05-22
**Статус:** `Затверджено`
**Контекст:** Фаза 0 — визначення стека для всієї екосистеми

## Контекст

Проєкт має три компоненти (Сайт, CRM, QA-бот) і центральну сутність `Vehicle` зі складною state machine. Ключові вимоги: SEO для каталогу авто, phone OTP auth, shared types між фронтом і бекендом, складна бізнес-логіка (стани, ролі, наряди). Деплой — окремий сервер, налаштовуємо пізніше.

## Зафіксований стек

### Монорепо
**Turborepo** — єдиний репозиторій для Сайту, CRM та API.
Спільний пакет `@auto/types` — типи Vehicle, User, ServiceRecord та інші описуються один раз і шаряться між усіма компонентами.

### Сайт (Фасад) — Фаза 1
- **Next.js 15** (App Router) + TypeScript
- SSR/SSG для SEO каталогу авто

### CRM (Бек-офіс) — Фаза 2
- **Refine.dev** + Next.js + TypeScript
- Підключається до того самого NestJS API

### Backend API — Фаза 1+
- **NestJS** + TypeScript
- Модульна архітектура, Dependency Injection
- Guards для ролей (клієнт / адмін / механік)
- OpenAPI spec генерується автоматично з декораторів

### База даних
- **PostgreSQL** — основна БД
- **Prisma ORM** — schema-first, автогенерація TypeScript-типів, міграції

### Черги та кеш
- **Redis** + **BullMQ** — черги для SMS-відправки, майбутніх нотифікацій

### Автентифікація
- **Кастомний Phone OTP** в NestJS
- SMS-шлюз: Turbosms або SMS-Fly (UA)
- Логіка: Shadow (phone-only) → Registered (phone + пароль)

### QA/Security Bot — Фаза 5
- **Playwright** (E2E / браузерні тести)
- **k6** (навантажувальне тестування)
- **nuclei** або **OWASP ZAP** (security)

## Чому саме це

- **TypeScript наскрізно** (Next.js + NestJS): shared types, одна мова, немає розсинхронізації між фронтом і беком
- **NestJS над Fastify/Express**: state machine Vehicle і складна роль-система вимагають структурованої архітектури з DI
- **Prisma над TypeORM**: кращий TypeScript DX, schema.prisma як єдине джерело правди для БД
- **Refine.dev**: економить 60-70% часу на CRM — готові таблиці, фільтри, форми

## Наслідки
- Позитивні: один стек → менше контекст-свічінгу, shared types → надійність, NestJS → чиста масштабованість
- Компроміси: NestJS має більше boilerplate на старті, але це окупається при зростанні складності
