## Context

Проєкт стартує з нуля. Обрано стек: Turborepo монорепо, Next.js 15 (App Router) для сайту, NestJS для API, PostgreSQL + Prisma як основна БД, Redis + BullMQ для черг. Фаза 1 охоплює тільки Сайт (Фасад) — CRM та QA-бот є предметом наступних фаз. Розробник один, macOS Apple Silicon.

## Goals / Non-Goals

**Goals:**
- Монорепо з shared TypeScript типами між site і api
- Схема БД для Phase 1 сутностей (User, Vehicle, Booking, ServiceRecord)
- Гостьовий флоу запису без реєстрації (тільки телефон)
- OTP-аутентифікація та конвертація shadow → registered акаунту
- Особистий кабінет "Гараж" з переліком авто та сервісною книгою
- Docker Compose для локальної розробки (PostgreSQL + Redis)

**Non-Goals:**
- CRM (Фаза 2)
- Каталог авто — буде в наступному кроці Фази 1, але поза scope цього change
- Vehicle state machine та зміна власності (CLIENT ↔ COMPANY) — Фаза 2/3
- Real-time статус авто в сервісі
- Оплата
- Push-нотифікації
- Панель адміністратора

## Decisions

### D1: Turborepo монорепо зі shared types

**Рішення:** Єдиний git-репозиторій, структура:
```
apps/
  site/     ← Next.js 15
  api/       ← NestJS
packages/
  types/     ← @auto/types — shared TS типи та Zod-схеми
  db/        ← Prisma schema + generated client
```

**Чому не окремі репо:** shared TypeScript типи між фронтом і беком — ключова вимога. Монорепо дозволяє `import { BookingDto } from '@auto/types'` і в Next.js, і в NestJS без дублювання. Turborepo забезпечує паралельний build і кешування.

**Альтернатива:** OpenAPI-generated client (окремі репо + codegen). Відхилено: зайвий крок у workflow, типи генеруються, а не пишуться вручну — втрачаємо контроль.

---

### D2: Vehicle завжди створюється при booking, навіть з пустими полями

**Рішення:** При гостьовому записі система завжди створює запис `Vehicle` в БД, навіть якщо клієнт не надав деталі авто. Всі поля крім `id` є nullable. Адмін підв'язує деталі через CRM пізніше.

**Чому:** Забезпечує цілісність FK (`bookings.vehicle_id NOT NULL`). Дозволяє адміну в CRM завжди мати об'єкт для редагування. Гараж клієнта може показати "Авто без деталей" з підказкою заповнити.

**Альтернатива A:** `vehicle_id` nullable в bookings. Відхилено: порушує реляційну цілісність, ускладнює запити.
**Альтернатива B:** `vehicle_hint` поля (вільний текст). Відхилено: втрата структури, адмін мусить парсити текст.

---

### D3: Телефон як первинний ідентифікатор користувача

**Рішення:** `users.phone` — `UNIQUE NOT NULL`. Всі інші поля (name, email, password) — nullable для shadow-акаунтів. Shadow конвертується в registered через OTP.

**Чому:** Телефон є обов'язковим при будь-якому записі (бізнес-вимога). Це дозволяє знайти існуючий профіль без реєстрації і запропонувати підтягнути історію.

**Ризик:** Phone number recycling — оператор перевидав номер іншій людині. Митигація: при конвертації shadow → registered завжди показувати клієнту його попередні дані для підтвердження.

---

### D4: SMS через BullMQ-чергу, не синхронно

**Рішення:** SMS ніколи не відправляється синхронно в рамках HTTP-запиту. Завжди через BullMQ job queue.

**Чому:** HTTP-відповідь клієнту не повинна залежати від доступності SMS-шлюзу. Retry-логіка при невдачі. Можливість throttling.

**Альтернатива:** Синхронна відправка. Відхилено: будь-яка затримка SMS-шлюзу = timeout для клієнта.

---

### D5: Prisma як ORM, schema-first підхід

**Рішення:** `packages/db` містить `schema.prisma` як єдине джерело правди для БД. Prisma Client генерується і шариться між api та майбутніми скриптами.

**Чому над TypeORM:** Prisma генерує повністю type-safe client без декораторів. Кращий DX для міграцій. `schema.prisma` читається як документація.
**Чому над Drizzle:** Prisma зрілішаI, більше прикладів для NestJS, краща документація.

---

### D6: Garage — читає тільки Сайт, пише тільки CRM (service records)

**Рішення:** У Фазі 1 Сайт може лише читати `ServiceRecord`. Створення записів — виключно задача CRM (Фаза 2). Сайт показує те, що є в БД.

**Наслідок для Phase 1:** Гараж може бути "пустим" (немає сервісних записів) — це нормально. Покажемо порожній стан з поясненням.

## Risks / Trade-offs

- **[SMS-шлюз недоступний]** → OTP не доставлено, клієнт не може увійти. Митигація: retry у BullMQ (3 спроби з backoff), fallback-повідомлення клієнту про затримку.
- **[Phone recycling]** → новий власник номера бачить чужу пропозицію "підтягнути історію". Митигація: показуємо ім'я та дату останнього запису — клієнт сам вирішує.
- **[Дублювання vehicle]** → клієнт записується двічі з різних пристроїв, без деталей авто — два порожніх vehicle record. Митигація: в CRM адмін мерджить дублікати (Фаза 2 task).
- **[Nullable поля vehicle в Гаражі]** → клієнт бачить "авто без назви". Митигація: UI показує placeholder "Деталі уточнюються" + номер booking як ідентифікатор.
